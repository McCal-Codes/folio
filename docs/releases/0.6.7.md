# Folio 0.6.7: what supporters tested, plus seven fixes

0.6.7 is one release, not two. Supporters have been on `0.6.7-beta.2` since 22 Sep, which carried the Supporter
badge, the Supporters list, Folio Beta in the Market and the two-pane layout. The seven fixes landed on `main` a day
later. Shipping either half alone under this number would take something away from somebody, so 0.6.7 is both.

Both halves are on `main` now: the fixes in #81, the supporter half in #89. This release is what is left after that,
which is the notes, the roadmap and the version.

`versionCode` is **6070** for `0.6.7-beta.3` and `0.6.7` alike, where the published `0.6.7-beta.2` was 607 under the
older formula (ADR 0007 gave every release nine spare numbers so a fix like `0.6.7.1` can exist). Codes only rise, so
beta.2 still installs into beta.3. Android refuses only a *lower* versionCode, and `SoftwareUpdate.isNewer` orders by
the version name, so `beta.2 < beta.3 < 0.6.7`. Every step installs over the last.

## 1. beta.3, for supporters

The first build with both halves, and the first that supporters get **through the Market** rather than by hand:
beta.2 put the broker's address in the app, so Market › Sources › Folio Beta should now offer beta.3 by itself. That
path has never carried a real build, which is reason enough for this beta to exist.

Build and sign it the usual way (release keystore, the same key as 0.6.6, or it will not install over anything):

```bash
FOLIO_RELEASE_STORE_FILE=/path/outside/the/repo/folio-release.jks FOLIO_RELEASE_STORE_PASSWORD=… FOLIO_RELEASE_KEY_ALIAS=… FOLIO_RELEASE_KEY_PASSWORD=… ./scripts/release-signed.sh
```

The script now refuses to build when the tag already exists, when the changelog has no section for the version, or
when the working tree is dirty. A beta may be built while its section still says `Unreleased`; a stable may not.

Publish it as a pre-release on `McCal-Codes/folio-beta`, the way [0.6.7-beta.2.md](0.6.7-beta.2.md) describes, then
check the part that matters: on a phone already carrying beta.2, Market › Sources › Folio Beta offers beta.3, and
Update Now installs it. If that works, no later beta needs handing out by hand.

What to ask supporters, in the order things are likely to be broken:

1. **Did the beta arrive by itself?** That is the whole point of this build.
2. **Background › Android wallpaper, then swipe between pages.** This is #12/#35, the oldest open bug. On a phone
   that had it, it should be clean from the first swipe, folded and unfolded.
3. **Settings unfolded and upright**, where the list isn't pinned: every page should have something that reads as a
   way back.
4. **The Supporter badge** is still there after the code runs out, and Settings › Supporters lists whoever said yes.

## 2. 0.6.7, for everyone

Same tree, one commit later: `folioVersion` to `0.6.7`, the changelog section dated, the roadmap's 0.6.7 items from
`building` to `done`. Build, sign, publish on `McCal-Codes/folio`.

That commit is dated 2026-09-26. beta.3 was never built: everything it would have carried, plus #148, #155, #156 and #158,
went out under the stable number instead, which REL-15 allows because no beta.3 was ever published.

Before sending it:

- Publish the SHA-256 next to the download, in whatever message carries the link.
- Run the APK through VirusTotal and link the report. A sideloaded launcher holding `REQUEST_INSTALL_PACKAGES`
  usually collects a heuristic flag or two from small engines; saying so up front reads better than letting someone
  find it.
- Point at [PERMISSIONS.md](../../PERMISSIONS.md). 0.6.7 asks for nothing 0.6.6 didn't.
- Supporter codes carry over untouched. Nobody has to redeem anything again.

## 4. Not in this one

- The language, Home and Smooth work is **0.6.8** now. It used to be called 0.6.7; the number moved when the fixes
  and the supporters' beta both landed on it.
- Dev Mode (branch `dev-mode`) is a long way behind the supporter work it overlaps with, and rebases after this.
- The dependency bumps waiting in Dependabot: the two test-only ones are safe whenever, Coil and the Compose BOM are
  not going into a release that already carries this much, and the `com.android.library` bump is wrong as written
  because it leaves `com.android.application` behind (REL-28).

## 4a. Known, and left for 0.6.8

The code review before the bump found nothing that blocks this release. These are real but small:

- `MarketHost.applyTweak` resolves Flipbook through the whole tweak table, so a Market bundle carrying it sets it
  while the gate is closed. Nothing draws, but the Tweak Library hides it, so it cannot be switched off until 0.6.8.
- `LauncherScreen.kt:240` reads the Flipbook gate once, so a beta code entered after Home is up needs Home recreated.
- `Diagnostics.artRefused` can carry an absolute file path when a wallpaper write fails on a full disk, and
  `pinRefused` names the requesting app. Both go against what the trail's header promises.
- `backgroundUnreadable` logs on every failed decode, so a missing photo can fill the 40-line trail with one line.
- A shortcut Folio refuses after `accept()` stays pinned in Android with nothing on Home.
- `PinWidgetActivity` checks providers through package visibility, so a widget-only app with no launcher activity
  is refused. Folio's picker cannot see those either, so nothing that worked before stops working.
- The onboarding chip still uses the `folio_dunes` key. Its text already says "Folio background".

## 5. What this release taught us

Two branches held two different meanings of "0.6.7" for a day, and the stable would have been offered to supporters
as an update that removed four features. [docs/standards/releases.md](../standards/releases.md) is the result, and
`tools/check-release-rules.sh` plus the guards in `scripts/release-signed.sh` are what enforce it.
